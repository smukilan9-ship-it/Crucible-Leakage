Why this matters

A leaked column makes every number better, right up until it doesn’t.

01

The failure looks like success

A column that records why the outcome happened is perfectly correlated with it. The model learns to read the answer instead of predicting it. Accuracy climbs, the validation score climbs with it, and nothing anywhere reports a problem. The model ships.

02

Cross-validation cannot see it

Splitting the data does not help, because the leaked column sits on both sides of every split. Each fold independently confirms the model is excellent. This is structural: no amount of resampling, nesting, or holding out catches a column that was contaminated before the split was drawn.

03

Statistics point the wrong way

The obvious defense is a correlation threshold, and it fails in both directions. On Titanic, boat correlates −0.013 with survival and decides it outright, while sex correlates −0.529 and is entirely legitimate. A threshold keeps the leak and deletes the real signal.

04

The information is in the name

A person reading autopsy_code in a mortality table knows instantly, without computing anything, because the name says where the value comes from. That reasoning is semantic, not statistical, which is exactly why a language model can do it and a correlation cannot.

Without a browser

The same audit, from a terminal

This page and the command line call the same function, so the two cannot drift apart. Use the terminal when you have more than one table, when the audit belongs in a pipeline, or when the column names should not leave your machine until you say so.

Stage 3

Which model reads your columns

This choice is not cosmetic, and the models fail in a specific way. Asked about leakage, they read the question as being about timing. In the benchmark behind this tool, across ten models from eight laboratories, recall averaged 97% on columns recorded after the prediction point and 89% on columns that exist because the outcome happened, but only 62% on columns that record why a label was assigned — and eight of the ten scored worse on that third kind than on the second in the very same tables. Every model here is sent a clause written to close that gap. The card says how far it closed, and under which wording, because no wording works uniformly across models.

Detection

What the screens found

Stage 5 · human in the loop

Nothing is dropped without you

The screen has found columns whose meaning encodes the outcome — the kind a correlation test is blind to by construction. That is the work it saves you: you no longer have to read a data dictionary line by line looking for them. What it does not do is decide. A column can be flagged and still be one you need, and only you know your data well enough to say so. Accept the set as it stands, or change it.

Three ways a column can leak, and one verdict that is yours

The first three name how the outcome got into the column; they are accounts, not severities. The fourth is not a mechanism at all — it is what the tool says when it has found something arguable and declines to decide for you.

REASON

The column was an input to deciding the label. Whoever assigned the outcome looked at this value to do it, so the model is reading the decision, not predicting it.

e.g. the diagnostic code a claim was rejected for, when predicting rejection
CONSEQUENCE

The column exists only because the outcome happened. Its presence or absence is the label, whatever the value says. This is the one that survives a correlation check, because on the rows where the outcome did not occur the column is simply empty.

e.g. a lifeboat number, when predicting survival
TIMING

The value is recorded after the moment you said the prediction happens. It may be perfectly ordinary data; it just will not exist yet when the model has to run.

e.g. total length of stay, when predicting at admission
CONTESTED

Flagged, but the documentation says the value was already fixed at the prediction point — so it could honestly have been obtained. A prior estimate of the target is the standing example: using it is usually a bad idea, and that is a judgement about what your model is for, not about whether the value was available.

Orders
The columns are read three times in three different orders, because order alone changes what a model flags. Each filled dot is one order that called it a leak; the majority settles it.
|r|
Correlation with the target, ignoring direction. The statistical screen flags anything above 0.5.
Agreement
Which screens flagged it. Model only is the interesting case: a real leak whose correlation is far too low for any threshold to catch. Statistics only is usually a strong but legitimate predictor.
Stage 6

What the leaks were buying

Each model is fit twice: once with every column, once with your confirmed drops removed. Same folds, same encoding, and the same hyperparameter search on both arms, so the cleaned fit is the best version of itself rather than a strawman. There is no comparison against ground truth here, because your data does not come with one — the honest number is simply what the model can do without reading the answer.

Edit the column set

The comparison above used the set you confirmed. Change it here — drop something else, or put a column back — and measure again. Nothing is locked in; disagreeing with the screen is a legitimate result, not a mistake.
